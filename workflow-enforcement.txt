Problem summary
---------------

The GreenID Epic workflow did not enforce the intended manager/assignee loop.

Expected workflow:

1. Manager opens an Epic and moves ordered tasks to To Do.
2. Manager assigns the first task only.
3. Assignee starts that task by moving it to In Progress.
4. Assignee moves completed work to Review.
5. Manager reviews.
6. If accepted, manager moves it to Done.
7. PM automatically assigns the next unassigned To Do task in the same Open Epic to the same assignee.
8. If manager posts feedback instead, assignee prioritizes that feedback before taking new work.

Observed failures:

- Proposal-applied assignments changed task rows but did not wake the assigned agent.
- The assignee stayed in To Do and did not move the task to In Progress.
- Karen did not alert because ai-monitor was crashing before it could complete a run.
- Karen was also not reliably reading the active worktree database.
- The review_done workflow stopped at Done and did not assign the next Epic task.
- GreenID task ranks were reversed from the intended dependency order after proposal apply.
- Karen's Jira receiver was disabled/stopped, causing an additional monitor health failure.
- After deployment, the task page hit a runtime error because cached Date fields came back as strings.


Root causes
-----------

1. Missing notification path in work-item proposal apply

   Normal task create/move/update paths call sendTaskWorkflowNotification().
   The work-item proposal apply path in ai/web/lib/work-items/apply.ts directly
   applied task.assign and task.acting_manager updates but did not send workflow
   notifications after commit. The DB looked right, but the agent was not woken.

2. No automatic next-task assignment after manager acceptance

   The agent workflow endpoint handled review_done by moving the current task to
   Done, but it did not find and assign the next task in the same Epic.

3. Karen monitor crash

   /usr/local/bin/ai-monitor crashed with KeyError: 'age_s' while building its
   compact input. Some stalled-task rows use session_idle_s rather than age_s.

4. Karen monitor database drift

   ai-monitor was not explicitly tied to the active worktree DB. The active PM
   service used /etc/default/pm-active-worktree, but ai-monitor only read its
   own config/env/hardcoded fallback paths.

5. pm-workflow-nudge environment drift

   pm-workflow-nudge only sourced /etc/default/pm by default. It needed the
   active worktree env file too, otherwise recovery nudges could run against
   the wrong app root or DB.

6. Live GreenID task order was wrong

   Proposal task creation processed independent operations backward. The
   resulting ranks made the last logical task appear before the next actual
   implementation task. Auto-handoff depends on rank order, so the live data
   needed correcting and the proposal apply loop needed fixing.

7. Cached Date serialization

   Next unstable_cache can return serialized strings for Date fields. The task
   page assumed Date objects and called .toISOString(), causing production task
   pages to throw.

Branch changes and rationale
----------------------------

ai/web/lib/work-items/apply.ts

- Added workflow notification dispatch after proposal application.
- Added task comment notification dispatch after proposal-applied comments.
- Added taskWorkflowBody() helper for consistent Backlog, To Do, Review, and Done prompts.
- Sends backlog_plan_requested when an assigned task is created in Backlog.
- Sends todo_start_required when an assigned task lands in To Do.
- Sends review_requested when a task is moved to Review.
- Sends review_done when a task is moved to Done.
- Resolves reviewer as acting manager, Open Epic acting manager, or reporter.
- Runs notifications after the DB transaction with Promise.allSettled() so notification failure does not roll back proposal application.
- Fixed pending create operation processing to preserve forward dependency/rank order instead of processing independent ops backward.

Why:

- Proposal apply was the missing trigger path for the GreenID task.
- Agents must be woken whenever applied work changes assignment/status.
- The rank order fix prevents future Epic task ordering reversals.


ai/web/app/api/agent/tasks/[taskId]/workflow/route.ts

- Added epicId to task selection.
- Added assignNextEpicTaskAfterDone().
- On review_done, after moving the current task to Done, PM finds the next unassigned To Do task in the same Epic ordered by rank and createdAt.
- Assigns that next task to the completed task's assignee.
- Sets acting manager to the existing next-task acting manager or the current reviewer.
- Logs task.assign and task.acting_manager activity.
- Sends todo_start_required to the assignee.
- Revalidates current task, next task, and project board.
- API response now includes nextTask when an automatic handoff occurred.

Why:

- The manager acceptance step must drive the next unit of work without manual latency.


ai/web/lib/agents/task-workflow-notifications.ts

- Updated workflow prompt rules.
- Review rule now says review_done auto-assigns the next unassigned To Do task in the same Open Epic.
- Assignee rule now explicitly prioritizes review feedback before newly assigned To Do work.

Why:

- The agents needed explicit workflow semantics in their PM context.


ai/web/app/(app)/projects/[slug]/board-client.tsx

- Added a Workflow focus panel above the board.
- Focus order: Review, To Do, In Progress, assigned Backlog.
- Added workflow pills on focus cards and task cards:
  Review now, Start now, Assign first, Complete or update, Plan due.
- Added owner labels explaining who should act next.

Why:

- The web interface goal is zero latency. The board should surface the next
  actionable workflow item rather than making users infer it from columns.


ai/web/app/(app)/projects/[slug]/tasks/[taskId]/page.tsx

- Added dateValue(), dateIso(), and updated timeAgo() to accept Date or string.
- Replaced direct task.createdAt/task.updatedAt/attachment.createdAt .toISOString() calls.
- serializeActor() now handles avatarUpdatedAt as Date or string.

Why:

- Cached server data can return date fields as strings. Production task pages
  were failing at runtime after rebuild/restart.


ai/openclaw/bin/ai-monitor

Expected behaviour after the fix
--------------------------------

- Applying a proposal that assigns a task wakes the assignee.
- Applying a proposal comment wakes mentioned/relevant agents.
- Assigned Backlog tasks ask the assignee for a plan/opinion only.
- Assigned To Do tasks ask the assignee to move to In Progress and start work.
- In Progress stale tasks are visible to Karen's PM workflow monitor.
- Moving a task to Review wakes the resolved reviewer.
- review_feedback leaves the task in Review and wakes the assignee.
- Assignees prioritize review feedback over new To Do work.
- review_done moves the task to Done, then auto-assigns the next unassigned To Do task in the same Open Epic to the same assignee.
- The board highlights the workflow items most likely to require immediate action.
