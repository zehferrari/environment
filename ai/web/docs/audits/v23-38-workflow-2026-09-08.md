# V23-38 workflow audit — 2026-09-08

Audited Task `cmtrzl2edjd5gov2ks78ojgwq` in project `v23` through the live

## Findings and corrections

1. **Revised plans silently lost their reviewer wake.** Revision 1 was
   submitted at 11:42:39 and reviewed at 11:47:06. Carmen submitted revision 2
   at 11:50:40, but no new review notification followed. Both submissions
   occurred at workflow version 0. The outbox used
   `task:v0:action-plan-review:reviewer`, so its completed first-plan effect
   suppressed the new submission. The owner's 12:49:11 message led to a third
   revision and a separate reply-path notification at 12:58:40, ending a
   68-minute wait. The submit-plan executor now scopes the notification key
   to the plan ID and revision persisted in the same transaction. Receipt
   replay still prevents duplicate revisions and duplicate notifications.

2. **Approval dispatched work before preparation finished.** Approval at
   13:00:16 generated an immediate assignee turn telling it to wait. Worktree
   preparation generated another turn at 13:00:30, canceling the first with
   `run superseded before replacement dispatch`. Approval now only schedules
   preparation; that procedure owns the single wake after preparation succeeds.

3. **Starting implementation canceled the agent that had just started.** At
   13:00:47, the authenticated start command committed an execution episode
   and returned `actionEffect=continue`. Its procedure then opened episode 2
   and dispatched another turn at 13:00:48, canceling the continuing start
   turn and leaving two open episode records. The procedure now recognizes
   command-owned episode/continuation state in its durable receipt and skips
   the extra episode and dispatch. Starts without authenticated execution
   bookkeeping retain the procedure-owned fallback.

4. **The task context API omitted the structured Action Plan.** The inline
   episode brief is bounded, but `buildTaskContextJson` did not query or return
   the Action Plan at all. A fresh episode therefore could not retrieve the
   complete criteria from the advertised task context endpoint. Both history
   modes now return the canonical plan, revision, approval, ordered steps,
   and parsed acceptance criteria. Existing task access checks still apply.
