# PM deployment notes (HOMELAB-43, Stage 1)

This directory carries the deploy-side artefacts for the PM walking skeleton.
It does not auto-apply — the bootstrap is intentionally manual for Stage 1 so
the operator sees exactly what changes on the host.

> **Agent read-API (loopback only)**: PM exposes
> `GET /api/agents/context/{task,epic,project}/<id>` for OpenClaw agents to
> retrieve live PM state on demand instead of receiving it inlined in every
> turn. Authenticated with the same `channels.pm.token` agents already have.
> Loopback-only — nginx must NOT proxy these paths. Full contract: see
> [`../docs/agent-pm-api.md`](../docs/agent-pm-api.md).

## Worktree switcher (live preview)

Lets the monitor agent build any git worktree and flip which one `pm.service`
serves and which source tree `pm-consumer.service` uses — from the CLI
(`pm-switch <wt>`) or, in the PM webapp, a git/worktree-exposed project's
**Settings → Worktree live preview** panel (human sessions only; agents are
rejected — a stricter admin-only gate is still pending). The currently served
worktree exposes **Rebuild live**, which runs the same monitor-driven switch
pipeline against the active branch without changing worktrees. The admin can
use **Remove local** on a non-live, non-protected linked worktree. It removes
only a clean worktree; generated `public/version.json` build stamps are discarded.
An attached local branch is deleted even when it is unmerged, while remote branches
and per-branch preview databases remain. Install with
`sudo PM_MONITOR_USER=<monitor-user> ai/web/deploy/install-pm-switch.sh` (after
`code-tree-perms` has made `/srv/Code` group-collaborative). Full design,
mechanism, and caveats: [`MULTI_AGENT_WORKTREES.md`](./MULTI_AGENT_WORKTREES.md).
The installer writes a root-owned, non-secret `/etc/default/pm-deploy` contract
from its repository/worktree, code-group, database, pnpm, lock, spool, and env
file options. That contract preserves custom paths across the monitor runner
and its sudo boundary; see `pm-deploy.env.example`. Runtime credentials remain
in `/etc/default/pm` and are never copied into the deployment contract.

The same Settings panel serves every project registered in
`lib/deploy/switch-registry.ts` (ENV-107 generic stack), not just PM:
**wdt** (`node-service` behind `worktree-preview@wdt.service`) and
**patricia** (`nginx-docroot` — docroot symlink + nginx reload). Their
spools live at `/var/lib/worktree-switch/<key>` and are consumed by
`worktree-switch-runner@<key>.service`; each project's contract lives in
`/etc/worktree-preview/<key>.env`, installed by
`worktree-preview-install.sh`. Re-run the relevant installer after changing a
runner helper; it now restarts the runner so the installed Python process loads
the update. The installers also create root-owned operation locks under
`/var/lib/worktree-locks`, shared only for flock access by `code-agents`.
Generic project spools are private to the runner and the configured PM web
user (`PM_WEB_USER`, default `karen`) through ACLs.

If a switch or local removal reports `WORKTREE_LOCK_FILE missing`, the generic
stack was only partially upgraded: the helper is newer than that project's env
contract, and the operation lock may not exist. Do not retry the removal until
the contract is reconciled. From this repository's deployed worktree, repair
Patricia idempotently with:

```sh
sudo ai/web/deploy/worktree-preview-install.sh patricia
sudo ai/web/deploy/worktree-preview-install.sh status
```

The project installer first stops every active generic runner that consumes
the shared helpers and takes each project's operation lock (waiting for an
in-flight CLI switch/removal to finish). It preserves existing lock inodes,
atomically replaces the selected project's env contract, verifies the lock
declaration, releases the locks, and reloads the runners so they all use one
helper version. The temporary stop also prevents an old runner from
interpreting `remove` as a request to serve that worktree while the contract
is being repaired.

**Database model per project.** PM (`environment`) and WDT run
`DB_ENGINE=sqlite`: every branch deployment gets its own database
(`wt-<branch>.db`) forked once from the canonical seed and migrated
before the build, so schema *and data* can differ between branches.
Patricia runs `DB_ENGINE=none`: the switcher never touches a database,
so all Patricia branch deployments share whatever database the PHP app
is configured against.

### Live rebuild troubleshooting

For worktree deployments, `pm-switch` is the live-site deployment boundary.
Do not use the legacy direct rebuild path against a managed worktree. If
`rebuild-and-restart.sh` is pointed at `/srv/Code/environment.worktrees/...`,
it delegates to `pm-switch` so Prisma generated-client ownership, per-branch
SQLite forks, `pm.service`, and `pm-consumer.service` are handled together.
Do not manually edit or stage deployment artifacts through the primary
`/srv/Code/environment` checkout; make changes in a branch/worktree and switch
with `pm-switch`.

Browser-triggered rebuilds run as the monitor service user, not as the human
who last built the worktree. The switch pipeline therefore calls the privileged,
path-validated helper twice before building:

- `pm-apply-worktree --stop-live <standalone> <db-url>` stops `pm.service` and
  `pm-consumer.service` when the target worktree or DB is already live, avoiding
  SQLite locks and `.next/standalone` rebuild races.
- `pm-apply-worktree --prepare-build <ai/web> <db-url>` removes generated
  `.next` and Prisma client artifacts and recreates the Prisma output directory
  for the actual builder user. This avoids `EACCES` failures when a previous
  build was made by a different local account.

If the browser shows a 502 after **Rebuild live**, check
`journalctl -u pm-switch-runner.service -n 160 --no-pager` and
`/var/lib/pm/switch/state.json`. After fixing the cause, recover with
`pm-switch <worktree-name>` from a local operator shell, then verify
`pm-switch status` and `curl -I http://127.0.0.1:<pm-port>/login`.

### "Site is rebuilding" page (graceful 502)

During the ~2-5s flip when `pm.service` restarts, the upstream is unreachable
and nginx would return a raw 502. Instead it serves
`/var/www/pm-maintenance/rebuilding.html` — a self-contained, animated page that
polls `/login` and reloads itself the instant the new build answers `200`.
Because it triggers on upstream availability (not on a branch), it covers every
worktree/branch automatically and also softens genuine crashes.

Two pieces, both in this directory:

- `rebuilding.html` — the static page. `install-pm-switch.sh` copies it to
  `/var/www/pm-maintenance/rebuilding.html` (root-owned, world-readable).
- `nginx-mission-control.conf` — the `error_page 502 503 504 /rebuilding.html;`
  block plus the `internal` `location = /rebuilding.html` and
  `proxy_intercept_errors on;` in `location /`.

Apply on the host:

```sh
sudo PM_MONITOR_USER=<monitor-user> ai/web/deploy/install-pm-switch.sh   # stages the page
sudo cp ai/web/deploy/nginx-mission-control.conf /etc/nginx/sites-available/<pm-hostname>
sudo nginx -t && sudo systemctl reload nginx
```

Verify without a real deploy by stopping the app briefly:
`sudo systemctl stop pm.service` → load the site (you should see the rebuilding
page) → `sudo systemctl start pm.service` (the page reloads into the app on its
own within a few seconds).

## Branch-push verifier (Review verification)

When an assignee moves a code-touching task (`branchName` set on a project
with `repositoryPath`) to Review through the workflow endpoint with
`repoTouched: true` (default for branch-bearing tasks), PM drops a JSON job
into `/var/lib/pm/branch-verify/<jobId>.json`. The repo-fetch-user
`pm-verify-runner.service` picks it up, finds the active PM worktree (by
reading `pm.service`'s `WorkingDirectory`), and runs the TS verifier
(`ai/web/scripts/pm-verify-branch-pushed.ts`) inside it. The verifier:

- `git -C <repositoryPath> fetch --quiet origin main <branchName>` on the local
  clone, then verifies current `origin/main` is an ancestor of
  `origin/<branchName>` — the remote IS Bitbucket, but the runner reuses the
  SSH credentials configured for `PM_VERIFY_RUN_USER` on the local clone (no
  Bitbucket REST in this pass);
- resolves the local branch worktree when available and fails fast if it still
  has uncommitted changes;
- pushes clean local branch commits to `origin/<branchName>` when the local
  branch is ahead and the runner has write credentials;
- looks for a commit on `origin/<branchName>` whose subject starts with the
  resolved COMMIT_PREFIX (`task.commitPrefix` → fallback `epic.commitPrefix`);
- checks the matching commit author and committer against the effective git
  identity (`Project.defaultGitUserName/defaultGitUserEmail`, falling back to
  system settings) when one is configured;
- if the verified branch is the currently served PM worktree, rebuilds and
  restarts the live PM service before releasing the task for review;
- writes a monitor-authored task Comment plus a `pm.repo.verify.ok` or
  `pm.repo.verify.fail` `ActivityLog` row.

If `pm.repo.verify.fail` reports `Unauthorized`, `permission denied`, or
`Could not read from remote repository`, that is a monitor verifier
credential problem. Set `PM_VERIFY_RUN_USER` to a local account that can fetch
the project repository, add that account's SSH public key as a read-capable
Bitbucket repo/workspace key, or configure an equivalent read-only deploy key,
then re-trigger `ready_for_review`. `PM_MONITOR_USER` is only the PM identity
used for verifier comments and activity rows.

The reviewer is only woken after `pm.repo.verify.ok`. If verification fails,
the assignee is woken to commit/push/fix the branch unless the failure is a
monitor repository-access problem. The task page also shows a Review
verification panel reading the latest `pm.repo.verify.*` row, so humans can see
why the review is waiting. Install with
`sudo PM_MONITOR_USER=<monitor-user> PM_VERIFY_RUN_USER=<repo-fetch-user> ai/web/deploy/install-pm-verify.sh`.

## Deployment Approval Credentials

Deployment approval is a write path, separate from the read-only Review
verifier above. The PM consumer runs the deployment monitor under the
configured monitor service account. It uses that account's Git/SSH
configuration to check for uncommitted local changes, commit them only after
human approval in the Development tab, verify and push the source branch, then
uses Bitbucket's REST API to open, approve/merge, and monitor provider PRs.

Required host checks for every replicated server:

- The PM consumer unit must keep the monitor account home readable to
  OpenSSH (`ProtectHome=read-only`, not fully hidden), even when pnpm
  `HOME` is redirected to `/var/lib/pm/pnpm-home`.
- The monitor account's SSH public key must have write access to the
  project repository or workspace. A key that authenticates to the Git
  provider but is not authorized for the specific repository will fail
  deployment approval with `Unauthorized` / `Could not read from remote
  repository`.
- The PM service environment must include Bitbucket API credentials with
  pull-request write permission:
  `BITBUCKET_USERNAME` (or `BITBUCKET_USER`) plus
  `BITBUCKET_APP_PASSWORD` (or `BITBUCKET_TOKEN`). These are used only for
  provider REST calls such as creating, approving/merging, and polling pull
  requests; they do not replace the monitor account's SSH key for git
  fetch/push.
  Put them in the base PM env file (`/etc/default/pm` by default). The
  worktree switch helper copies that file into the generated active env file
  (`/etc/default/pm-active-worktree` by default) during `pm-switch`; rerun
  `pm-switch <worktree>` after changing deployment credentials so both
  `pm.service` and `pm-consumer.service` inherit the new values.
- The project repository path in PM must point at a clone whose `origin`
  remote resolves to the expected provider repository. If project-specific
  provider workspace/repo settings are blank, PM falls back to parsing
  that remote URL.

## Service Model

`pm.service` is one host-wide web service for the configured PM hostname. It is
not started once per agent. The single PM process owns the UI, DB,
task/comment persistence, and native `pm` channel callbacks, then
routes work to each agent through that agent's loopback OpenClaw
gateway.

The service user is currently the monitor agent account because it has
host-level visibility into the local agent fleet. A future dedicated `pm`
Unix user is still the cleaner long-term option; set
`PM_APP_USER` / `PM_APP_GROUP` when running `openclaw/install.sh` to
render the units for a different service account.

`pm.service` needs write access to `/srv/agents/Pictures` for manual
profile/avatar uploads on agents created with the `Manually Uploaded` image
theme. The OpenClaw lifecycle helper also creates per-agent picture directories
with `code-agents` group-write permissions so image-generation agents can write
the generated `profile.png` and `avatar.png` files.

The PM units are host-wide system services. Their unit files are
root-owned under `/etc/systemd/system`, while the runtime processes use
the configured PM service account. Do not install or enable
`pm.service` or `pm-consumer.service` under
`/home/<agent>/.config/systemd/user`; `openclaw/install.sh` removes
those stale per-agent user units during PM reconciliation.

`pm-consumer.service` keeps `ProtectHome=read-only`. Deployment approval
runs Git as the monitor user, and OpenSSH reads that user's
`~/.ssh/known_hosts` and private key from the login home even though
`HOME` is redirected for pnpm. Fully hiding home directories causes
deployment pushes to fail with host-key/SSH permission errors. To avoid
`pnpm` probing service-user config files, the unit points `HOME`,
`XDG_CONFIG_HOME`, `XDG_CACHE_HOME`, `PNPM_HOME`, and
`NPM_CONFIG_USERCONFIG` at service-private directories under `/var/lib/pm`.
Existing installs can apply the committed drop-in
`deploy/systemd/pm-consumer-monitor-home.conf` as
`/etc/systemd/system/pm-consumer.service.d/30-monitor-home.conf`.

## First-time install

```bash
# 0. Install host packages required by the app and deploy helpers. package.json
#    pins pnpm 10.33.0; Node 20+ is supported (current hosts use Node 24).
# openSUSE:
sudo zypper --non-interactive install sqlite3
# Debian/Ubuntu:
# sudo apt-get install sqlite3
# If the pinned pnpm is not already installed:
# sudo npm install -g pnpm@10.33.0
node --version                    # >= 20
/usr/local/bin/pnpm --version    # 10.33.0 on replicated hosts

# 1. Start from the standard collaborative managed-worktree layout described in
#    MULTI_AGENT_WORKTREES.md, then install the exact locked dependencies.
WORKTREE=/srv/Code/environment.worktrees/main
APP="$WORKTREE/ai/web"
# Replace these examples with the checkout owner and PM monitor/runtime account.
PM_REPO_USER=owner
PM_APP_USER=monitor
PM_APP_GROUP=monitor
sudo -u "$PM_REPO_USER" pnpm --dir "$APP" install --frozen-lockfile

# 2. Create the host-private runtime env before any migration. Keep production
#    SQLite data private to the monitor/runtime account. Set DATABASE_URL to
#    file:/srv/Data/pm/pm.db plus host URLs and fresh secrets.
sudo install -d -o "$PM_APP_USER" -g "$PM_APP_GROUP" -m 0770 /srv/Data/pm
sudo install -o root -g "$PM_APP_GROUP" -m 0640 \
  "$APP/deploy/pm.env.example" /etc/default/pm
sudo $EDITOR /etc/default/pm

# 3. Render/reconcile host-wide units, runtime directories, token maps, gateway
#    hooks, and the native PM channel. The tracked pm*.service files are render
#    templates with host-specific defaults; never raw-copy them into systemd.
sudo PM_WEB_ROOT="$APP" PM_APP_USER="$PM_APP_USER" \
  PM_APP_GROUP="$PM_APP_GROUP" PM_NODE_BIN=/usr/bin/node24 \
  PM_PNPM_BIN=/usr/local/bin/pnpm \
  "$WORKTREE/ai/openclaw/install.sh"

# 4. Install the managed switch boundary and its non-secret host contract.
sudo PM_MONITOR_USER="$PM_APP_USER" \
  PM_REPO_ROOT=/srv/Code/environment \
  PM_WORKTREES_ROOT=/srv/Code/environment.worktrees \
  PM_DB_DIR=/srv/Data/pm PM_PNPM_BIN=/usr/local/bin/pnpm \
  "$APP/deploy/install-pm-switch.sh"

# 5. Seed/migrate the canonical DB explicitly, then switch to main. The first
#    switch forks wt-main.db, applies pending migrations, builds, starts both
#    services, and verifies the login page plus a hashed asset.
sudo -u "$PM_APP_USER" env DATABASE_URL=file:/srv/Data/pm/pm.db \
  /usr/local/bin/pnpm --dir "$APP" exec prisma migrate deploy
sudo -u "$PM_APP_USER" /usr/local/sbin/pm-switch "$WORKTREE"

# 6. Render and review the real nginx template for this hostname/certificate,
#    install it, and validate before reload.
PM_HOSTNAME=mission-control.example.com
sed "s/mission-control\.example\.com/$PM_HOSTNAME/g" \
  "$APP/deploy/nginx-mission-control.conf" > "/tmp/$PM_HOSTNAME.conf"
sudo $EDITOR "/tmp/$PM_HOSTNAME.conf"
sudo install -o root -g root -m 0644 "/tmp/$PM_HOSTNAME.conf" \
  "/etc/nginx/sites-available/$PM_HOSTNAME"
sudo ln -sf "/etc/nginx/sites-available/$PM_HOSTNAME" \
  "/etc/nginx/sites-enabled/$PM_HOSTNAME"
sudo nginx -t && sudo systemctl reload nginx

# 7. Persist services and verify.
sudo systemctl enable --now pm.service pm-consumer.service
/usr/local/sbin/pm-switch status
curl -fsS -o /dev/null http://127.0.0.1:3000/login
```

Existing single-checkout databases can be relocated safely with
`move-sqlite-db.sh` before enabling worktree forks. It takes a SQLite backup,
enables WAL, updates `/etc/default/pm`, and restarts the units.

## Subsequent host releases

Use the guarded repository-owned updater instead of hand-sequencing Git,
migrations, builds, and restarts. It refuses dirty, local-ahead, detached, or
diverged worktrees; performs only a fast-forward; installs the frozen lockfile;
refreshes `/usr/local/sbin` helpers plus `/etc/default/pm-deploy`; and delegates
the live migration/build/restart/asset checks to `pm-switch`:

```bash
# thinkpad
sudo ai/web/deploy/update-managed-host.sh \
  --worktree /srv/Code/environment.worktrees/main \
  --repo-user zeh --monitor-user karen --branch main

# yoga510
sudo ai/web/deploy/update-managed-host.sh \
  --worktree /srv/Code/environment.worktrees/main \
  --repo-user rachael --monitor-user emery --branch main
```

Thinkpad serves `https://agents.vixi.au`; yoga510 serves
`https://agents.eurekafiles.com`. Each host keeps its own secrets, token maps,
agent registry, database, TLS files, and nginx site. Do not commit `.env*`,
`/etc/default/pm`, token/credential maps, SQLite/WAL files, `.next`, generated
Prisma clients, or `node_modules`.

## Subsequent migrations

For schema changes after Stage 1: generate the migration locally with
`pnpm prisma migrate dev --name <change>`, commit the new directory under
`prisma/migrations/`, and release with `update-managed-host.sh` or
`pm-switch <worktree>`. The switcher applies `prisma migrate deploy` to the
branch's live `wt-<branch>.db` before it builds or restarts either service.
Running migration only against canonical `pm.db` does not update an existing
live branch database.

`pnpm prisma db push` is dev-only (rapid prototyping without a migration
history) and **must not** be used against the production DB.

## Native OpenClaw PM channel

PM direct chat, task chat, task-comment, and Epic chat replies use the
native OpenClaw `pm` channel. Each enabled local agent gateway must load the staged plugin
at `/usr/local/share/openclaw/plugins/pm-channel` and have a channel
config similar to:

```json
{
  "channels": {
    "pm": {
      "enabled": true,
      "token": "env:PM_OPENCLAW_CHANNEL_TOKEN",
      "callbackToken": "env:PM_OPENCLAW_CHANNEL_TOKEN",
      "callbackUrl": "http://127.0.0.1:3000/api/openclaw/pm-channel/reply",
      "agentId": "main"
    }
  }
}
```

PM posts accepted turns to:

```text
POST http://127.0.0.1:<gateway_port>/pm-channel/ingest
Authorization: Bearer <PM_OPENCLAW_CHANNEL_TOKEN>
```

The route uses `auth: "plugin"` and performs its own Bearer check, so
it does not require gateway operator credentials. Keep gateways bound to
loopback and do not expose `/pm-channel/ingest` through nginx.

For live chat UX, PM includes a stream callback URL in each turn. The
plugin posts partial reply chunks to
`http://127.0.0.1:3000/api/openclaw/pm-channel/stream`; browsers subscribe
to PM over same-origin SSE while final durable replies still land at
`/api/openclaw/pm-channel/reply`.
Direct-chat pages reconcile saved replies through the lightweight
`GET /api/agents/<slug>/chat/messages` endpoint if the browser misses a
final stream event. This avoids full-page polling while preserving the
server-rendered page as the source of truth.

PM resolves channel tokens in this order:
`PM_OPENCLAW_CHANNEL_TOKEN_<AGENT_SLUG>`,
`/etc/openclaw/pm-channel-tokens.json`, then
`PM_OPENCLAW_CHANNEL_TOKEN`. The installer writes the per-agent token
file and mirrors those values into the gateway configs. When no
`--agents` override is passed, the installer discovers enabled agents
from `/etc/openclaw/agents.json`; `openclaw/install.sh` passes that
registry explicitly.

When `openclaw-pm-channel/index.js` changes, reinstall the staged plugin and
restart affected gateways. Running gateways keep the old plugin module in
memory until restart, so a source-only deploy is not enough:

```bash
sudo node deploy/install-openclaw-pm-channel.mjs --registry /etc/openclaw/agents.json --restart
```

`openclaw/install.sh` also applies the host runtime patch
`openclaw-patch-session-fence`. Without it, an OpenClaw provider timeout
can append an empty assistant error record, trip the embedded session
takeover guard, and bypass configured model fallbacks. Re-run the
OpenClaw installer after any global `openclaw` package update.

## Local OpenClaw wake hooks

The PM consumer should wake agents through each local gateway's external
hook:

```text
POST http://127.0.0.1:<gateway_port>/hooks/wake
Authorization: Bearer <agent hooks.token>
```

`openclaw/install.sh` is responsible for enabling this on the host. For
every enabled agent with an `openclaw-gateway` listener in
`/etc/openclaw/agents.json`, it should bind the gateway to loopback,
preserve the existing `hooks.internal` config, and set:

```json
{
  "gateway": {
    "bind": "loopback",
    "trustedProxies": ["127.0.0.1", "::1"]
  },
  "hooks": {
    "enabled": true,
    "path": "/hooks",
    "token": "<per-agent secret>",
    "allowRequestSessionKey": true,
    "allowedSessionKeyPrefixes": ["hook:", "pm:"]
  }
}
```

The same token must be mirrored into
`/etc/openclaw/pm-consumer-tokens.json` under that agent's slug. The
token file should be `0640` and owned by `root:<pm-consumer-group>`
using the configured PM consumer group. The committed service file is only a
template; `openclaw/install.sh` renders the installed unit with
`PM_CONSUMER_USER` / `PM_CONSUMER_GROUP` or the PM app user/group defaults.
Native PM-channel chat dispatch is bus-first: PM writes
`openclaw.pm_channel_turn` envelopes to `PM_CHANNEL_BUS_DROP_DIR`, and
`pm-consumer` reads them from `PM_CONSUMER_DROP_DIR`. On the standard
file-drop deployment both variables should point at `/var/lib/pm/drop`.
The worktree switch helper preserves this setting in
`/etc/default/pm-active-worktree`; without it chat jobs remain queued and
fail with `PM channel bus disabled`.
Keep direct HTTP as fallback only: set
`PM_OPENCLAW_CHANNEL_HTTP_FALLBACK=1` only when the bus is unavailable
and localhost gateway HTTP should be used as a temporary degraded path.
Agents stay warm via their stable per-scope OpenClaw session key
(`pm:<scope>:agent:<slug>` in `AgentSessionBinding`), which OpenClaw reuses
across turns. Accepted-to-first-stream latency beyond
`PM_OPENCLAW_FIRST_STREAM_WARNING_MS` writes a
`pm.channel.latency_warning` audit row.
OpenClaw requires `hook:` in the allowed session-key prefixes when no
default hook session key is configured; PM chat/comment routing uses
`pm:` keys created in `AgentSessionBinding`.

After hook changes, restart the affected `openclaw-gateway.service`.
Expected checks per gateway are: `GET /health` returns 200,
`GET /hooks` returns 405, unauthenticated `POST /hooks/wake` returns
401, and authenticated `POST /hooks/wake` returns 200. `ss -ltnp`
should show `127.0.0.1:<gateway_port>`, not
`0.0.0.0:<gateway_port>`. If the OpenClaw dashboard is exposed through
nginx, proxy it to `127.0.0.1:<gateway_port>` and explicitly block the
prefixed hook path (`/<agent>/hooks`), because the dashboard proxy strips
the public prefix before forwarding to the gateway.
The legacy monitor wake helper remains only as a fallback for old hosts
or temporary hook failures.

## Seeded credentials

- **Bootstrap human user** — configured through the bootstrap-owner environment
  variables. Its password is active immediately and is never forced to rotate.
- **Each co-located agent** — random password written to
  `/etc/openclaw/pm-agent-credentials/<agent>.json` (mode `0600`, owner
  `<pm-app-user>`). The credential is host-private and never logged.

The boot-time sync (in `instrumentation.node.ts`) reads
`/etc/openclaw/agents.json` by default,
reconciles the `Agent` table, and seeds the user rows + credential files. The
same path also runs on a 5-minute interval — see `AGENT_SYNC_INTERVAL_MIN`.

## Acceptance check (Stage 1)

After install:

1. `curl -I https://<pm-hostname>/login` -> `200 OK`.
2. Sign in as the bootstrap owner -> the requested workspace opens directly.
3. `/agents` lists each configured local agent, including the monitor agent.
4. Create a project → /projects/<slug> board loads with 5 columns.
5. Add a task → drag across columns → reload, position persisted.
6. `journalctl -u pm.service` shows one `[pm] boot sync` log line and then a
   `[pm] periodic sync` line every 5 min.
